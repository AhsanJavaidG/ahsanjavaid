Overview

Turning tribal knowledge into a scalable product.

Ops had built a working system — but it lived in their heads and inboxes. The product had to expose that logic without dumbing it down. That meant treating the design as an interface to a domain, not just a set of screens.

// context

Enterprise operators sending 100k+ SMS bursts, drip flows, and transactional alerts across 40+ markets. Every ops person had their own spreadsheet, methodology, and vocabulary.

// my role

Lead designer, partnered with a PM and a squad of 6 engineers. Owned discovery, IA, component design, spec, and production QA.

// approach

Jobs-to-be-Done to frame outcomes over features. Card sort to shape navigation. Component-first design in Figma before any screens existed.

Jobs-to-be-Done

Six job statements ran the whole product spec.

When engineers debated an implementation, we came back to these. When PM prioritized a sprint, we ranked against these. Written by users in their own words, sharpened by me for reuse.

// JTBD_01 · launch

When I'm preparing a Black Friday burst, I want to schedule and rate-limit sends so I can hit peak revenue windows without triggering carrier throttling.

// JTBD_02 · segment

When I'm targeting opt-in customers by market, I want to build reusable audiences from live data so I can stop re-exporting CSVs for every campaign.

// JTBD_03 · compose

When I'm writing a message, I want to preview SMS and RCS side-by-side with real merge fields so I can catch broken personalization before send.

// JTBD_04 · route

When a message fails to deliver, I want to fall back to a cheaper channel automatically so I can reach the customer without ballooning cost.

// JTBD_05 · prove

When finance asks what a campaign earned, I want to attribute revenue by audience segment so I can defend the marketing budget.

// JTBD_06 · trust

When a customer replies STOP, I want to see the opt-out honored across every future campaign so I can stay compliant with market regulators.

Information architecture

Users grouped by lifecycle, not object type.

Hybrid open/closed card sort with 12 ops and marketing users across 3 markets. My mental model was wrong twice — users think in campaigns, drilling down. The final IA reflects their words.

// nav-model.json · signed off by 12 users
// Root object: campaign const nav = { "dashboard": // live health, delivery, spend "campaigns": { "draft": [...], "scheduled": [...], "live": [...], "archive": [...] // each owns → audience, template, schedule, routing, attribution }, "audiences": { "segments": // rule-based, live, "lists": // uploaded / synced }, "templates": // SMS + RCS in one library "analytics": // delivery, engagement, attributed revenue "settings": { "senders", "compliance", "opt-outs", "billing" // STOP handling lives here, not per campaign } };
A

"Campaign" is the noun that matters.

Users didn't think in templates or audiences first. They thought in campaigns and drilled into the components. The nav had to reflect that primacy.

B

Opt-outs deserved settings, not campaigns.

Compliance was a global concern, not per-campaign. Users needed to trust that STOP replies were honored everywhere by default — no toggle.

C

Analytics is a mode, not a page.

Every object had numbers on it. Analytics as a top-level tab held cross-cutting reports; contextual metrics lived inline on each object.

D

Empty states are onboarding.

Emerged mid-sort: for a greenfield tool, the empty state is the tutorial. We built a library of guided empty states for every entity.

Four modes of one object

Compose · Schedule · Monitor · Analyze.

One campaign lives across four modes. Each is a different screen but they share the same header, breadcrumbs, and inline metrics — so context never resets.

Compliance by design

Consent, opt-out, and accessibility — built as first-class objects.

A messaging platform lives or dies on trust. STOP replies aren't a feature — they're a design primitive. Every screen assumes the recipient is one bad experience from unsubscribing.

// GDPR · Art. 6 + 7

Opt-in lists are audited at import time. Every audience row carries its consent source, timestamp, and market. Compliance officers can trace any send back to the moment consent was given.

audit_trail = { consent_source, timestamp_utc, market, subject_id }
// STOP handling

Global, not per-campaign. A STOP reply in one send propagates to every future campaign across all markets in under 60 seconds. No toggle. No exception path.

// WCAG 2.2 AA

Keyboard shortcuts for every canvas action. Screen-reader labels on every node. High-contrast variant tested against 4.5:1 on the dark theme.

// Rate + revoke

Sender rate limits visible on every campaign. Audience revocation clears queued messages for the revoked subject before send.

// Data residency

EU-only processing. Market-scoped audiences never cross regions. Enforced at IA level, not runtime.

Reflection

What JTBD did for us — and what I'd change.

What worked

The six job statements became acceptance criteria for every sprint. When engineers proposed a shortcut, we asked "which job does this serve?" and the answer usually resolved the debate.

The biggest win was shared language. PM, design, and eng finally used the same nouns for the same things.

What I'd change

Run the card sort earlier — before wireframes. Two weeks wasted on a nav I assumed was obvious.

Invest in an in-product empty state library from day one. For a greenfield tool, empty states are onboarding.
